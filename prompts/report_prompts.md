# PADER-Style Safety Reporting — Master Prompt Specification

## 1. Purpose

This document defines the prompt contract used by the PADER-style pharmacovigilance reporting pipeline.

The language model is a **controlled narrative generation component** only.

The core design principle is:

> **Deterministic Python calculates and owns the facts. The language model verbalizes those facts. Validation determines whether generated text may be accepted.**

The language model must never become the source of truth for case counts, reaction counts, percentages, dates, trends, seriousness classifications, outcomes, or regulatory actions.

---

## 2. Model and Generation Contract

**Current implementation model:**

`Qwen/Qwen2.5-0.5B-Instruct`

The model receives:

1. A controlled system message from `llm_pipeline.py`.
2. One section-specific user prompt generated by `prompts.py`.
3. A compact, section-specific subset of the validated Evidence JSON.

The model must return only the requested report section.

Generation is deterministic:

- `do_sample=False`
- `num_beams=1`
- bounded `max_new_tokens`
- no-repeat n-gram constraint
- CPU-compatible inference

The exact runtime generation parameters are controlled by `llm_pipeline.py`, not by this document.

---

## 3. System-Level Model Instruction

The runtime system message is:

> You are a controlled pharmacovigilance reporting assistant. Use only the supplied evidence. Return only the requested report section. Do not repeat the instructions.

This system instruction establishes the model's role but does not replace section-specific grounding instructions.

---

## 4. Global Grounding Rules

Every generated section must follow these rules.

### Evidence

- Use **only** the supplied Evidence JSON.
- Treat the supplied evidence as the sole factual source.
- Do not use general medical knowledge to fill missing information.
- Do not use information from the original dataset that is not present in the supplied evidence.
- Do not introduce external sources.
- Do not invent facts, numbers, dates, reactions, outcomes, classifications, or events.

### Numerical information

- Do not calculate new statistics.
- Do not recompute percentages.
- Do not derive counts from other counts.
- Do not perform arithmetic on evidence values.
- Use numerical values exactly as supplied by the evidence.
- Preserve the meaning and association of each numerical value.

### Dates and trends

- Do not invent dates or reporting periods.
- Do not reconstruct monthly data.
- Do not change a supplied year, month, or date.
- Use only deterministic trend values supplied in the evidence.
- Do not calculate a new trend from monthly values.

### Clinical and safety interpretation

- Do not infer causality.
- Do not state or imply that a product caused an event.
- Do not infer expectedness.
- Do not infer clinical significance.
- Do not declare a confirmed safety signal.
- Do not convert a frequency observation into a causal or clinical conclusion.

### Regulatory language

- Do not recommend withdrawal, discontinuation, contraindication, dose changes, or other regulatory action unless that exact information is explicitly supplied in the evidence.
- Do not invent regulatory decisions or safety actions.
- Do not describe an alert or expedite classification as a confirmed safety signal.
- If regulatory-action information is unavailable, state that it was not supplied rather than inferring an action.

### Terminology

- Preserve reaction terminology from the evidence.
- Do not replace supplied reaction names with synonyms when doing so could change traceability.
- Do not introduce medical terminology that is not supported by the evidence.

### Style

- Use concise, neutral, professional pharmacovigilance language.
- State observations rather than interpretations that exceed the evidence.
- Avoid persuasive or speculative language.
- Do not mention the prompt, model, Evidence JSON, tokenizer, validation code, or generation process.
- Return only the requested section text.
- Do not repeat the instructions.

## 5. Section-Specific Prompt Contract

The pipeline currently generates five LLM-assisted sections.

---

# 5.1 Narrative Summary

### Objective

Produce a concise narrative overview of the supplied case, seriousness, demographic, reaction, outcome, and alert evidence.

### Prompt

Write a concise narrative summary using only the supplied evidence.

Only use information provided in the evidence section passed to you.

Do not invent, infer, or create new evidence or information.

Do not calculate statistics or percentages.

Use the supplied values exactly as provided.

Preserve the terminology used for reactions and seriousness categories.

Do not infer causality, clinical significance, expectedness, or a confirmed safety signal.

Do not make regulatory recommendations.

If an item is unavailable in the supplied evidence, do not invent it.

Write grammatically correct, concise, neutral regulatory-style prose.

Return only the final narrative summary.

---

# 5.2 Summary Analysis

### Objective

Summarize the overall deterministic safety-analysis findings without independently calculating or interpreting unsupported conclusions.

### Prompt

Write a concise summary analysis using only the supplied evidence.

Cover the relevant case counts, seriousness information, demographic distributions, reaction findings, available outcomes, and deterministic trend summary contained in the evidence.

Use only the supplied values.

Do not calculate, recompute, or derive statistics.

Do not change percentages, counts, dates, or trend values.

Do not infer causality, clinical significance, expectedness, or a confirmed safety signal.

Do not introduce information that is absent from the evidence.

Do not make regulatory recommendations.

Use neutral, factual pharmacovigilance language.

Return only the final summary analysis.

---

# 5.3 Reaction Analysis

### Objective

Describe deterministic reaction-level findings.

### Prompt

Analyze the supplied reaction evidence and write a concise regulatory-style summary.

Cover, where supplied:

- Total reaction occurrences.
- Number of unique reaction terms.
- Most frequently reported reactions.
- Most frequently reported serious reactions.
- Reaction concentrations supplied by the evidence.

Use only the supplied reaction evidence.

Do not calculate reaction frequencies, percentages, rankings, concentrations, or changes.

Do not create new rankings from raw values.

Do not rename or replace reaction terminology with unsupported synonyms.

Do not infer causality, clinical significance, expectedness, or a confirmed safety signal.

Do not describe a frequent reaction as evidence that the product caused the reaction.

If temporal reaction information is not supplied, do not invent temporal patterns.

Return only the final reaction analysis.

---

# 5.4 Serious and Alert Case Analysis

### Objective

Describe deterministic seriousness and alert/expedite findings.

### Prompt

Write a concise regulatory-style summary of the supplied serious and alert case evidence.

Cover, where supplied:

- Total unique cases.
- Serious cases.
- Non-serious cases.
- Unknown seriousness.
- Serious-case percentage.
- Expedite or alert cases.
- Expedite or alert percentage.
- Seriousness categories such as death, life-threatening events, hospitalization, disability, congenital anomaly, and other serious events.
- Available outcomes.

Use only the supplied evidence.

Do not calculate or recompute percentages.

Do not infer causality or clinical significance.

Do not describe an alert, expedite classification, or seriousness category as a confirmed safety signal.

Do not infer regulatory action.

Do not invent missing outcomes.

Return only the final serious and alert case analysis.

---

# 5.5 Trend Interpretation

### Objective

Verbalize deterministic temporal trend calculations already produced by Python.

### Prompt

Analyze the supplied temporal evidence and write a concise regulatory-style trend interpretation.

Cover, where supplied:

- Reporting period.
- Highest month.
- Lowest month.
- First month.
- Last month.
- Deterministic absolute change.
- Deterministic percentage change.

Use only the supplied values.

Do not calculate or recompute any change.

Do not reconstruct monthly counts.

Do not modify dates.

Do not invent months, years, quarters, or reporting periods.

Do not infer causality from an increase or decrease.

Do not describe a trend as a safety signal unless the evidence explicitly provides that conclusion.

Do not introduce clinical or regulatory conclusions.

Return only the final trend interpretation.

## 6. Evidence Presentation

The application should provide the model with a **section-specific compact evidence object**, not the entire raw dataset.

The compact evidence object is created by `prompts.py`.

This serves two purposes:

1. Reduce prompt size.
2. Reduce the opportunity for the model to use irrelevant information.

The compact evidence is a filtered representation of the deterministic Evidence JSON.

### Important rule

The compacting layer may **remove irrelevant fields**, but it must not:

- calculate statistics;
- modify values;
- derive new values;
- reinterpret classifications;
- generate narrative;
- introduce external information.

---

## 7. Deterministic vs. LLM Responsibilities

### Deterministic Python owns

- Data preprocessing.
- Case identification.
- Case counting.
- Seriousness classification.
- Demographic calculations.
- Reaction counting.
- Outcome analysis.
- Alert/expedite analysis.
- Temporal trend calculations.
- Evidence JSON construction.
- Methodology text.
- Limitations text.
- Human-review status.
- Final validation decision.

### LLM owns

- Converting supplied evidence into readable narrative prose.
- Improving grammatical quality.
- Organizing supplied observations into concise paragraphs.
- Producing section-specific regulatory-style wording.

### LLM does NOT own

- Numerical truth.
- Statistical calculations.
- Dataset interpretation.
- Causal inference.
- Regulatory decisions.
- Safety-signal confirmation.

---

## 8. Grounding and Validation Contract

Generated text must be validated after generation.

The current implementation includes lightweight validation for:

### Numerical grounding

Numbers appearing in generated text are compared with numerical values present in the Evidence JSON.

### Unsupported-claim detection

The validator flags potentially unsafe phrases such as:

- caused by
- causes
- caused
- proves that
- confirmed safety signal
- confirmed signal
- causal relationship
- causally related
- definitively related
- regulatory action
- should be withdrawn
- should be discontinued
- should be contraindicated
- clinically significant safety signal

These checks are intentionally conservative.

### Important limitation

Numerical membership validation alone does **not** prove that a number is associated with the correct evidence field.

Therefore, a validation pass must not be interpreted as a mathematical proof of factual correctness.

Human review remains required for the final PADER-style report.

---

## 9. Validation Failure Policy

If a generated section fails validation:

- Do not silently modify the generated text.
- Mark the section as requiring human review.
- Record the validation failure in the generation audit.
- Do not represent the generated section as fully validated.

The preferred production behavior is:

```text
LLM generation
      |
      v
Validation
      |
  +---+---+
  |       |
 PASS    FAIL
  |       |
  v       v
Accept   Reject / fallback
          |
          v
    Human review required
```

A deterministic fallback should be preferred over knowingly inserting an unvalidated narrative into a final regulatory report.

---

## 10. Output Restrictions

The model must never produce:

- A prompt.
- The Evidence JSON.
- A system message.
- Analysis of the instructions.
- Code.
- Markdown headings unrelated to the requested section.
- Invented case identifiers.
- Invented dates.
- Invented statistics.
- Invented regulatory actions.
- Causal claims unsupported by evidence.
- Clinical recommendations unsupported by evidence.

The model must output only the requested report-section prose.

---

## 11. Deterministic Report Sections

The following sections should remain deterministic and should not require LLM generation:

- Reporting Period
- Case Listing
- History of Actions
- Methodology
- Limitations
- Human Review / Review Status
- Evidence Traceability

These sections are intentionally deterministic because they do not require generative language to establish factual correctness.

If safety or regulatory action information is absent from the evidence, the report should explicitly state that the information was not supplied rather than infer or fabricate an action history.

---

## 12. Report Assembly

The final report should distinguish between:

1. Deterministically generated content.
2. AI-generated content.
3. AI-generated content that failed validation.
4. Content requiring human review.

The final report should not imply that AI-generated prose is automatically authoritative.

The intended workflow is:

```text
ICSR Dataset
     |
     v
Preprocessing
     |
     v
Deterministic Analysis
     |
     v
Validated Evidence JSON
     |
     +-----------------------------+
     |                             |
     v                             v
Deterministic Sections       Section-specific Evidence
                                     |
                                     v
                              Prompt Construction
                                     |
                                     v
                                    LLM
                                     |
                                     v
                              Generated Narrative
                                     |
                                     v
                               Validation Layer
                                     |
                              +------+------+
                              |             |
                             PASS          FAIL
                              |             |
                              v             v
                         Accepted       Review/Fallback
                              |             |
                              +------+------+
                                     |
                                     v
                              Report Assembly
                                     |
                                     v
                           PADER-Style Draft Report
                                     |
                                     v
                              Human Final Review
```

## 13. Human Review Requirement

This system is a **PADER-style report-generation prototype**, not an autonomous regulatory reporting system.

The generated report must remain subject to human review.

At minimum, reviewers should verify:

- Case counts.
- Seriousness counts.
- Reaction terminology.
- Outcome information.
- Trend values.
- Dates and reporting period.
- AI-generated narrative against the Evidence JSON.
- Unsupported or overly strong claims.
- Final regulatory wording.

The final status should remain:

`PENDING HUMAN REVIEW`

until a qualified reviewer verifies and approves the report.

---

## 14. Known Limitations

The current implementation uses lightweight grounding checks.

Known limitations include:

1. Numerical membership checks do not prove field-level correctness.
2. Phrase-based unsupported-claim detection cannot identify every possible hallucination.
3. Semantic equivalence between generated claims and evidence is not fully verified.
4. The LLM can produce fluent but incorrect wording even when individual numbers are present in the evidence.
5. Human review remains necessary.
6. A small language model may produce incomplete or grammatically imperfect output.
7. Model behavior can change with model/version changes.
8. Missing evidence must not be interpreted as evidence that an event did not occur.

These limitations should be stated explicitly rather than hidden.

---

## 15. Prompt Maintenance Rules

When modifying the prompt implementation:

1. Update `src/prompts.py`.
2. Keep the prompt documented in this file.
3. Keep the model name consistent with `src/llm_pipeline.py`.
4. Never introduce calculations into prompt construction.
5. Never pass unnecessary raw dataset information to the model.
6. Add a validation rule when a new high-risk claim type is introduced.
7. Test every changed section against known evidence.
8. Record important prompt/model changes in the project documentation.

`src/prompts.py` is the executable source of truth.

This document is the submission-facing prompt specification and documentation of the intended prompt contract.

---

## 16. Design Principle

The central safety boundary of the system is:

> **Facts are calculated deterministically; language is generated probabilistically; acceptance is controlled by validation and human review.**

The language model is therefore a presentation layer over validated evidence, not a replacement for the deterministic pharmacovigilance analysis.
